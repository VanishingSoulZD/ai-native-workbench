# 直接使用工作 Agent 完成研究：Case 001–004 中文会话示例

> 文档用途：在 Claude Cowork、Kimi Work 或其他具备多步骤执行能力的工作 Agent 中，直接委托本仓库的研究案例。
>
> 核心原则：以研究结果和真实交付物为中心。Research Charter 可以定义边界，但 AI Work Plan 不再是必经中间产物。
>
> 适用方式：将对应 Case 的会话示例整体发送给工作 Agent；若 Agent 能连接 GitHub，请它直接读取仓库文件并按权限完成文件交付。若无法连接仓库，则提供所需文件，并要求它把结果生成可下载/可导入的文件包。

## 1. 现在应该怎样与工作 Agent 对话？

### 1.1 不要只发送通用模板

“研究任务交付要求”这类通用模板，只规定结果质量底线，例如关键结论要有证据、数据要可追溯、文件要实际检查。它不能替代具体任务上下文。

每次正式委托至少需要让 Agent 明白：

1. **为什么做这项研究**：研究结果将支持什么理解或决策。
2. **具体要回答什么**：核心问题、子问题，以及明确不研究什么。
3. **研究对象和判定规则**：研究单位、分类定义、入选与排除规则；如有排名，要说明排名代表什么、不代表什么。
4. **什么算完成**：最终结论、重要数据、证据台账和实际交付文件的要求。
5. **已有上下文**：Research Charter、现有成果、数据文件、仓库路径、版本或研究截止日期。
6. **执行权限边界**：可以读取/创建/更新哪些内容；遇到无法访问或无法执行的操作时必须如实报告。

这六类信息不需要每次都变成六个复杂阶段。可以直接写进同一条委托消息，或者引用已有的权威文件。

### 1.2 Research Charter 还需要吗？

**它仍然有价值，但不需要把它变成每个任务的强制审批环节。** 建议按下面的方式决定：

| 情况 | 建议 |
|---|---|
| 一次性、边界明确的小型任务 | 在委托消息里写清目标、范围、交付要求即可；不必另建 Charter |
| 涉及多个研究问题、比较/排名、多类产物或跨多轮执行的大型 Case | 需要一份稳定的任务定义；可以是正式 Research Charter，也可以是内容完整的研究简报 |
| 仓库里已经有经批准的 Charter | 先读取并复用，不要为了使用工作 Agent 而重写一遍 |
| 旧 Charter 中的目标、时间截点或交付要求已经过时 | 让 Agent 识别差异；不要静默改写权威 Charter，应在执行简报中明确本轮更新，并将重要范围变化记录下来 |
| 任务只需一个 Agent 从头执行到交付 | **不需要**仅仅为了形式再生成 AI Work Plan |
| Agent 无法一次完成，或出现反复、权限、质量、成本上的具体缺口 | 再用简短计划或第二个 Agent 解决这个真实缺口 |

Research Charter 解决的是 **What / Why：要研究什么、为什么、范围与验收标准是什么**。AI Work Plan 解决的是 **How：具体调用哪些 AI、怎样分工和交接**。当工作 Agent 本身能够负责执行编排时，前者依然可能必要，后者不必由你预先另做一份。

### 1.3 对现有 Case 001–004 的建议

- **Case 001：**复用现有的 00-research-charter.md，但注意其研究日期是 2026 年 8 月，而且其中仍有“Research OS 实验”的方法论目标。本轮应该以研究结果为主要目标；将旧产物视为需要审查的历史材料，而不是必须原样继承的真相。若沿用原来的代表性排名口径，必须明确保留其定义，不能静默改成用户量排名。
- **Case 002：**复用现有的 00-research-charter.md。它已经定义 Work AI 的研究边界、全球代表 Top 10、中国代表 Top 5、产品工作定位和使用/编排问题。不要因为新执行方式而把研究缩减成普通产品清单；但可以把工作 Agent 能否直接生成证据和产物作为执行方式，而非主要研究结论。
- **Case 003：**当前 README 定义了研究主题，但本仓库尚未发现正式的 Case 003 目录或 Charter。下面的会话示例直接给出研究目标、范围、核心问题及产物要求；可以先执行，不必预先生成 Charter 和 Work Plan。如果以后需要分阶段、跨多轮继续研究，再将这份任务说明固化为 Charter。
- **Case 004：**当前 README 定义了 Deep Research Landscape，但本仓库尚未发现正式的 Case 004 目录或 Charter。下面的会话示例会把“产品能力盘点”与“同一真实任务的可验证输出比较”结合起来，避免最后只得到一份宣传文案式排行榜。它也不要求先生成 Work Plan。

### 1.4 推荐的实际操作顺序

1. 打开你准备使用的工作 Agent，选择一个新的、便于保存上下文的任务会话。
2. 粘贴对应 Case 的会话示例。如果 Agent 能访问 GitHub，先让它读取指定 Charter、仓库规范和历史产物。
3. 明确本轮是一次新的研究执行，不要只让它输出计划。让它自行拆解步骤并直接开展研究、创建产物和核查结果。
4. 若它不能访问 GitHub，就让它明确说明限制，并输出相同目录结构的完整文件包；不要接受“已写入仓库”之类未经证实的说法。
5. 交付后，检查研究结论、证据与实际文件。只有发现具体缺口时，才追加修复指令或引入第二个 Agent。

建议每次都让 Agent **先查看仓库现状，但不要先向你汇报一大段计划后等待批准**。如果存在实质性歧义，它应采用保守、明确的假设继续推进，并标记需要你判断的点；只有涉及不可逆操作、权限或范围重大改变时才应停下来征求确认。

## 2. 可复用的会话开场要求

下面这段可以放在各 Case 示例开头；如果 Case 示例已经包含相同要求，不需要重复粘贴。

~~~text
请直接执行这个研究案例，并以完成可核验的研究结果和实际交付物为目标。不要把生成研究计划、罗列建议或描述将如何完成当作最终交付。

请先读取本仓库中指定的 Research Charter、现有成果、相关项目约定和目录结构，并据此确定本轮实际需要完成的工作。把旧成果作为需要审查的材料，不要默认全部正确；同时不要无故重做已经符合本轮要求的内容。

请自主组织研究、资料检索、交叉核验、分析和文件生成。在适当情况下可以使用你具备的浏览器、代码执行、文件处理和已授权连接器。优先依赖可靠的一手来源；关键结论和数值要能追溯到具体来源，并区分事实、分析、判断、未验证信息和冲突证据。

请实际生成任务要求的文件并检查其存在、内容和相互一致性。若能够访问 GitHub，请按仓库现有约定写入适当目录；不要覆盖历史正式产物，除非已有明确的版本更新约定或我明确要求覆盖。若不能访问 GitHub，就生成完整、清晰命名的文件包，并说明需要我手工放置的位置。

不要默认需要多个 Agent 或多个研究产品。先尽可能使用你自身可用的能力完成任务；只有某个具体能力缺口会实质影响质量或完整性时，才使用第二个工具或提出升级方案。

最终报告必须列出实际完成的产物、关键结论和证据、未完成项、未验证或冲突内容，以及最需要我人工复核的事项。不要声称做过实际未执行的操作。
~~~

## 3. Case 001 — 2026 AI Coding Agent Landscape

### 使用前说明

仓库已有：

- Charter：cases/001-ai-coding-agent-landscape/00-research-charter.md
- 大量阶段研究材料、来源台账、候选池、Canonical Research Model、Research Note 及演示相关资产

本轮任务不是重新搭建 Research OS，也不是为了复刻原有阶段而产生尽可能多的文件，而是**重新确认当前 AI Coding Agent 市场结论是否仍成立，并交付一套有证据支撑的、可复核的研究成果**。可以复用有效的分类、定义和研究资产，但要重新验证容易过时的事实与排名。

### 可直接发送给工作 Agent 的完整会话

~~~text
请重新完成本仓库的 Case 001：AI Coding Agent Landscape。请直接开展研究并完成交付，不要先生成 AI Work Plan，也不要把研究流程本身或 Research OS 的工程建设作为本轮主要目标。

【权威任务上下文】
1. 首先读取 cases/001-ai-coding-agent-landscape/00-research-charter.md，理解并保留其中仍然有效的研究定义、候选范围、入选/排除规则和排名口径。
2. 读取该 Case 已有的主要成果，包括候选池、来源台账、研究结论、结构化数据以及演示产物，确认实际存在的文件后再决定如何复用。
3. 旧 Charter 的研究日期为 2026 年 8 月。请以本轮实际执行日作为当前研究截点，重新验证已经可能变化的产品能力、产品形态、价格/可用性、市场信号和关键引用。不要把旧报告中的时间敏感数据直接当成当前事实。
4. 旧 Charter 还包含“Research OS 实验”的目标。本轮以回答行业研究问题、提供可靠证据和交付可复用研究资产为主，不必为了完整复刻旧流程而重新生成每一个过程文档。

【核心研究问题】
截至本轮研究截点，全球 AI Coding Agent 市场中，哪些产品/产品家族最能代表市场重要性与技术/产品方向？它们各自代表什么产品形态、Agent 架构和 Software Engineering Workflow？哪些产品形成主流，哪些产品正在定义下一代方向？这些判断分别有哪些可靠证据？

请遵守现有 Charter 的研究单位和排名含义：以 Product / Product Family 为单位，避免同一家族的 CLI、IDE、Desktop、Cloud 多个入口重复占榜；不要把基础模型、纯补全工具或通用工作 Agent 自动算作 Coding Agent；如果沿用 Market Significance × Technology/Product Significance 的代表性排名口径，请明确这不是用户数排名，也不是纯功能分数排名。

【重点核查】
- 候选池是否覆盖主要全球与中国产品形态、商业产品和有代表性的开源产品；是否存在重要遗漏或重复别名。
- 代表性候选的入选、排除及顺序是否仍可由公开证据解释。
- 各产品的实际工作定位和端到端 Agent Loop：任务规划、上下文获取、工具调用、代码/环境修改、执行、验证、迭代修复、最终产物。
- 产品架构与执行形态：CLI、IDE、Desktop、Cloud、Sandbox、Context、Memory、MCP、Skills、权限和验证机制等。只记录有证据支持的能力，不要把厂商愿景等同于已经普遍可用的能力。
- 市场采用信号、第三方调查和公开 Benchmark 的口径、日期、样本与局限。不同来源的采用率、基准版本和评估配置不能随意混为一谈。
- 哪些结论是当前仍成立的，哪些已经过时、证据不足或存在来源冲突。

【必须交付的结果】
1. 一份清晰的执行摘要与最终市场判断。
2. 候选池及其分类、去重、入选/排除理由。
3. 最终代表性产品集与逐项证据依据。若证据不足以支持唯一排序，就采用分层/类别代表，而不是伪造精确名次。
4. 主要产品的能力与架构对比表，及对 Software Engineering Workflow 变化的综合分析。
5. 独立的来源/证据台账：关键主张、数据口径、来源 URL、发布日期/统计时期、支持内容、可信度与局限。
6. 结构化数据文件（优先沿用现有 Schema；如没有合适的，则使用易读的 CSV/JSON/Markdown 表格），并确保报告中的排名和数据表一致。
7. 对本轮主要交付物进行完整性检查，并列出关键未解决问题。

【执行及文件约束】
- 先检查仓库现状与现有约定，尽量复用有效成果；不要因为有旧文件就默认结论正确，也不要为了显示工作量重建不必要的基础设施。
- 对确实变化的事实进行当前核验。优先使用官方产品文档、正式公告、定价/帮助页面、公开榜单/论文和高质量独立资料；关键市场结论尽量进行交叉验证。
- 保留重要来源原文或准确的支持段落/数据位置，不能仅有一串主页链接。
- 不要无故覆盖既有正式产物。若没有适合的版本化约定，请将本轮更新产物集中保存到 Case 目录下的新版本/运行目录，并在摘要中说明如何与旧版本对应。
- 若无法访问或写入 GitHub，明确说明，并输出完整文件包；不要声称已经提交仓库。
~~~

【权威任务上下文】
1. 首先完整读取 cases/002-ai-work-agent-landscape/00-research-charter.md。该 Charter 定义本 Case 的主要范围、研究问题、术语、全球代表 Top 10、中国代表 Top 5 和证据要求。

4. 本轮优先回答“哪些 Work AI 能真正接手知识工作、完成什么任务、交付什么产物”，而不仅仅是总结市场功能或证明多 AI 编排的价值。

【核心研究问题】
1. Work AI / Work Agent / Office AI / Knowledge Work 的范围和边界如何定义？它们与 Research-only、Coding Agent、普通聊天助手、搜索产品及企业工作流平台的区别是什么？
2. 当前全球最具代表性的 10 个 Work AI 产品/产品家族是什么？中国市场最具代表性的 5 个是什么？它们是能解释市场结构的代表集合，不应伪装成具有绝对客观性的产品质量排行榜。
3. 每个代表产品的真实工作定位、可处理的任务类型、可用上下文、工具/连接器、自动执行能力、文件和产物能力、验证方式、人工介入边界分别是什么？
4. 面对研究、分析、写作、数据处理、文档与演示制作、跨应用操作、多步骤工作等实际任务，什么类型的产品适合直接承接整个任务？什么限制会迫使用户拆分任务或增加另一个工具？
5. 哪些产品已经能从任务目标直接走到完整交付？哪些主要仍是聊天/协作助手？哪些能力只是厂商宣称、预览或特定套餐可用？
6. 对个人用户、中国大陆用户与企业/团队用户，产品入口、权限、账号、地区和成本限制有什么重要区别？

【研究与判断原则】
- 以实际可执行能力为判定依据，不因厂商使用“Agent”命名就默认其自主程度更高。
- 对具体能力说明其产品入口、可用套餐/地区、预览状态与核验日期；不能把企业版或私有预览能力默认成个人用户可用。
- 全球和中国的候选范围都要充分覆盖后再筛选；说明入选与排除理由及边界案例。
- 每个关键判断必须有对应来源。官方文档用于确认产品支持什么；独立测评/真实使用证据用于补充它实际做得如何。二者要区分。
- 明确记录未知、证据冲突与无法验证的能力。
- 将“单个 Agent 是否足够”作为重要维度，不要预设所有任务都应该多 Agent 协作。

【必须交付的结果】
1. 研究结论与产品类别/市场结构概览。
2. 全球候选池、中国候选池及边界对象说明。
3. 全球代表 Top 10 和中国代表 Top 5，包含明确的选择逻辑与证据；如证据不支持精确排序，请采用类别代表或分层呈现。
4. 每个代表产品的中文能力卡片，至少包括：产品/厂商、主要入口、目标用户、实际工作定位、可处理任务、输入/上下文、执行与工具能力、文件/产物、连接器、验证能力、限制与可用性、证据链接和核验日期。
5. 一张“任务类型 → 适合的 Agent 能力 → 候选产品 → 能否直接交付 → 关键限制”的任务适配表。
6. 一份证据台账和可复用的结构化数据文件。
7. 结论应能回答：面对真实任务时，什么时候先交给一个工作 Agent，什么时候使用研究专用 Agent，什么时候需要人工拆分或多个工具接力。
8. 检查所有产物是否齐全、数据表和报告是否一致，并列出需要人工复核的关键点。

【执行及文件约束】
- 先检查已有目录和文件，复用有效分类、Schema 和产物；对明显过时的事实重新核验。
- 本轮不要求你实现新的 Agent、Research Runtime 或工具矩阵系统。

- 若无法访问 GitHub，输出完整文件包并标注每个文件应放置的仓库路径。

【研究目标】
帮助我为个人知识工作与 AI 编程建立可执行的模型、产品和套餐选择依据。我关心的不只是哪个模型的基准分数最高，而是：在真实可用的产品入口中，哪些模型/套餐适合什么工作、有什么限制、总体费用如何、哪些订阅或 Coding Plan / Token Plan 值得考虑。

【研究截点和适用人群】
- 以本轮实际执行日为研究截点，并在报告中明确日期。
- 面向个人/专业用户，必须单独标出中国大陆使用情境与全球服务情境的差异。
- 不得假设某款模型、产品、套餐或支付方式在我的账号、地区或设备上一定可用；对需要核查的项目记录实际证据和状态。
- 区分个人/消费套餐、企业套餐、API 计费、Coding Plan、Token Plan；不可将它们混为同一种成本。

【研究范围】
1. 主要模型家族及其对应的可用产品入口，覆盖推理/通用知识工作、长上下文、代码、结构化数据、视觉/多模态等关键能力。
2. 主流 AI 产品订阅：价格、计费周期、主要权益、使用额度/限制、模型/Agent/Research 等能力访问，以及地区或账号限制。
3. 专门面向编程的套餐或计划，包括它们覆盖哪些产品/模型、额度如何计算、是否有峰值/公平使用限制、超额后的收费或降级规则。
4. API/Token 计费：输入/输出价格、缓存/推理等差异计价项、上下文或速率限制，以及典型工作负载的估算方式。
5. 影响实际选择的条件：能力、稳定性、速率/额度、工具调用、文件/连接器、隐私与数据处理规则、地区可用性和总成本。

【需要回答的关键问题】
- 对复杂研究、日常问答/写作、长文档分析、数据表格处理、代码开发、Agent 多步骤执行，分别有哪些值得进入候选的模型/产品/计划？
- 订阅的实际价值如何评估？哪些能力是包含在套餐中的，哪些另行计费，哪些有使用限额或动态额度？
- Coding Plan 与直接 API 付费、通用订阅相比，在何种工作负载下更合算？有哪些不宜直接比较的计费口径？
- 当多个产品宣传相似能力时，怎样根据真实任务、可用入口和预算选出最小够用组合？
- 哪些关键事实因为地区、账号、动态定价或套餐条款而无法直接确认？

【数据与证据要求】
- 当前价格、权益、额度、地区和可用性优先使用厂商官方定价页、帮助文档、服务条款和产品说明，并记录核验日期。
- 数值必须注明币种、单位、输入/输出或其他计费类别、周期、税费是否包含（若能确认）、统计口径和来源。
- 将“官方公布价格”“第三方实测”“推算估值”分开标示。推算必须给出公式、假设和敏感性；不能拿单个基准分数直接推导通用能力。
- 对信息缺失、来源冲突、不同套餐不可比等情况明确标记，不要补造一个看似完整的表格。
- 由于此领域变化快，保留官方来源 URL、页面标题、检查日期和关键原文/数据位置。

【必须交付的结果】
1. 一份面向个人决策的研究报告，给出具体、附条件的选择建议，而不是无条件“最佳模型”排行榜。
2. 模型/产品/入口映射表，说明同一模型在不同入口中可能有不同限制。
3. 套餐对比表，包括价格、权益、额度、限制、地区/账号可用性和核验日期。
4. Coding Plan / Token Plan / API 的独立比较表，并清楚写明计费单位与不可比之处。
5. 至少三种示例工作负载的成本估算，例如：以研究为主、以高频编程为主、日常混合知识工作。写明用量假设和计算方式；不要伪造并不存在的固定额度。
6. 一份来源/证据台账，以及 CSV/JSON 等可复用结构化数据文件。
7. 一份未确认事项清单，以及在价格/额度变化时哪些字段需要重新核验的说明。

【执行及文件约束】
- 自主决定研究顺序，但不要先给我一份 Work Plan 后停止。
- 尽可能从当前官方资料取得可比较的事实；无法确认我的个人账号权限时，标记为“账号级未验证”，而不是推测可用。
- 不要为了得出结论而强行给全部厂商排唯一名次。按任务类型、使用地区和预算给出分场景结论。
- 如果本仓库还没有 Case 003 目录，请检查当前仓库约定，并在适当位置创建所需目录和实际交付文件；不要无谓创建大量阶段性文件。
- 最终检查报告与数据表是否一致，价格和套餐是否都有日期、币种、口径及来源。
~~~

## 6. Case 004 — Deep Research Landscape

### 使用前说明

该 Case 不能只比较各产品自称的“深度研究能力”。最有用的结果应包含两层证据：

1. **产品能力层**：当前可用入口、搜索和来源能力、计划/过程控制、引用质量、数据和文件导出、连接器与限制。
2. **实际任务层**：在相同研究问题、相同交付要求下，产品实际能否交付完整、可靠的数据和产物。

如果只收集功能介绍，无法回答你此前遇到的问题——报告看起来有结论，却缺少关键数据、独立证据表或可以继续使用的文件。

### 可直接发送给工作 Agent 的完整会话

~~~text
请完成 Case 004：Deep Research Landscape。请直接研究并交付完整成果。不要只写一份“各家 Deep Research 产品功能比较”或一个缺乏实测依据的排行榜。

【研究目标】
帮助我判断：面对需要多来源调查、关键数据支撑和可复用文件的研究任务，应该优先使用哪一类研究型 Agent/Deep Research 产品？各产品能可靠完成到什么程度？何时可以直接采用研究报告，何时需要工作 Agent 继续整理文件，何时需要独立核验？

【研究截点与范围】
- 以本轮实际执行日为研究截点，并明确产品、功能和套餐的核验日期。
- 覆盖主要国际产品及中国大陆用户值得关注的产品。研究型产品和通用/工作 Agent 中的研究模式可以纳入，但必须明确区分产品类别、入口和实际执行机制。
- 以可供个人或专业用户实际使用的产品为优先对象。企业专属、候补名单、预览版、地区受限或账号级功能应清楚标注。
- 主要研究单位是可供用户执行真实研究任务的产品/模式，而不是只比较基础模型的理论能力。

【核心研究问题】
1. 当前主要 Deep Research 产品分别能做什么？如何启动、指定来源、调整研究计划、上传文件、跟踪过程、查看引用和导出结果？
2. 引用是否能直接支撑具体结论？是否保留发布日期、统计时间、数据口径和原文位置？怎样处理冲突证据与信息缺失？
3. 产品能否输出独立的结构化证据表、候选清单、比较矩阵、CSV/XLSX/Markdown/Word 等文件？不能输出的格式应如何处理？
4. 产品是否具备连接器、浏览器/代码执行、文件写入、GitHub 等能力？这些是研究模式自身能力、同一产品另一模式的能力，还是外部工作 Agent 才能完成的能力？
5. 哪些产品特别适合不同类型任务，例如市场格局研究、时效敏感的价格/套餐对比、学术/技术研究、中文与中国市场研究、文件/数据密集型研究？
6. 报告长度、引用数量、产品宣传和研究质量之间是什么关系？哪些质量维度不能从宣传资料或单个 Benchmark 推断？
7. 什么时候一个 Deep Research 产品足够？什么时候需要第二个独立研究器、工作 Agent 或人工核验？

【实际任务验证】
请尽可能使用可实际访问的产品完成一项一致的小型对照任务，并保留实际产物。优先选择：
“研究当前主要 Work Agent / Office Agent，筛选一组有代表性的产品；提供入选理由、关键能力事实、当前可用性证据及可复用比较表。”

给每款实测产品使用同一版任务说明和相同的交付验收标准。记录产品/模式、测试日期、可用入口、输入任务、是否能生成证据表和独立文件、花费或额度信息（只有确实可观察时）、人工介入、完成时间（只有确实测量时）、主要错误/遗漏，以及实际输出文件。若无法访问某个产品或无法运行一致测试，明确标记“未实测”，不要伪装成对比结果。

同一产品应区分“官方说明支持”“本次实际观察到”“尚未验证”三类证据。无法控制模型、搜索索引、订阅额度或产品版本时，记录环境差异，不要将一次结果泛化为永久排名。

【统一验收标准】
- 是否回答了研究问题，而不是只写概述。
- 关键结论是否有可直接访问且内容匹配的来源。
- 关键数字是否包含单位、日期/期间和统计口径。
- 是否提供独立、可复用的证据表与结构化数据。
- 是否显式记录来源冲突、重要遗漏和不确定性。
- 是否真正生成要求的文件，文件是否可打开、字段是否齐全。
- 报告中的产品比较结论是否与证据和实际测试结果一致。

【必须交付的结果】
1. 产品/模式候选范围、类别划分及纳入/排除理由。
2. 主要 Deep Research 产品能力对比表，至少涵盖入口/可用性、研究过程、来源控制、引用和证据、结构化产物、文件导出、连接器/工具、限制及证据等级。
3. 基于证据的适用任务分析与条件化建议，而非没有统一依据的绝对排名。
4. 一组真实任务对照测试记录及可查看的原始产物（若本轮无法实测的产品要单独列明）。
5. 统一的研究验收清单、证据台账及结构化数据文件。
6. 对何时只用 Deep Research、何时交给 Work Agent 完成文件交付、何时增加独立复核的明确判断。
7. 对所有产物执行完整性检查，并列出哪些结论仅由厂商官方资料支持，哪些经过独立或实测证据验证。

【执行及文件约束】
- 直接执行，不要先生成 Work Plan 并等待确认。
- 研究产品本身的当前能力时优先使用官方文档、帮助中心、定价和正式发布说明；比较实际表现时，补充高质量独立证据和真实任务记录。
- 如果一个工作 Agent 同时具备 Deep Research 与文件处理能力，可以由它独立完成本 Case；不要为了形式必须再调用研究型 Agent。
- 如果本仓库没有 Case 004 目录，请按仓库约定创建最少量、清晰命名的交付文件；不要为了“研究系统完整”构建新的自动化平台。
- 不允许捏造测试耗时、费用、产品可用性或文件生成结果。无法验证的内容应清晰标记。
~~~

## 7. 执行后怎样验收工作 Agent？

不要只问“报告写得好不好”，而要检查这些可核验事项：

- **结论：**核心问题是否得到明确回答？有没有把产品宣传写成事实？
- **证据：**重要数值是否有原始来源、正确日期、单位、口径？来源是否真的支持旁边的结论？
- **覆盖：**候选池是否存在明显遗漏？筛选与排除是否解释得通？
- **产物：**报告、证据表和结构化数据是否实际存在？是否能独立使用？
- **一致性：**报告、表格、卡片里的产品名称、数据、排名是否一致？
- **当前性：**价格、功能、地区/套餐可用性及时间敏感事实是否在本轮核验？
- **透明性：**未验证、冲突、未实测和无法访问的内容是否被显式标记？
- **总成本：**是否还需要大量人工返工？相较直接聊天或 Deep Research，工作 Agent 真正省下了什么？

如果产物只是一篇长报告，说明研究可能完成了一部分，但不一定满足你的交付要求。反过来，即便文件很多，也不能证明研究质量高。

## 8. 如何将本轮经验回写到项目？

完成一个 Case 后，只沉淀可复用且经过验证的经验：

- 哪类任务可以直接交给一个工作 Agent。
- 哪些交付要求显著改善了证据和文件质量。
- 哪个能力缺口确实需要第二个产品或人工介入。
- 哪些验收检查能稳定发现错误。

不要因为一次执行不顺利，就立刻将流程扩展成新的通用系统；先确认该缺口是否重复出现、是否影响结果，以及最轻量的解决方式是什么。

**推荐的默认链路：**

~~~text
具体研究目标 + 充分的任务上下文（可引用 Research Charter）
                         ↓
           一个具备相关能力的工作 Agent
                         ↓
      研究 / 核验 / 分析 / 创建实际交付文件
                         ↓
               人工验收关键结论和产物
                         ↓
          只针对真实缺口补充工具或工作流
~~~

Research Charter 可以是稳定的任务定义；AI Work Plan 只是可选的规划资产。对于本项目后续的大型 Case，先把目标和验收标准说清楚，再让工作 Agent 直接完成工作，应成为默认实验方式。
